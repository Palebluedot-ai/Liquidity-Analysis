## BUG-001：连续测算覆盖历史报告

### 问题描述

用户完成一次测算后，点击报告中的“🔄 重新选择参数 / 测算其他币对与金额”，原报告会被查询表单替换。继续测算时，聊天记录无法保留完整的历次报告，影响不同币种、金额或方向之间的结果对比。

本问题指的是**历史报告被覆盖**，不是表单参数未保留。

### 复现步骤

1. 在 Lark / 飞书机器人聊天中打开测算表单。
2. 选择币种、方向、计价货币、金额和交易所，点击“立即测算”。
3. 收到测算报告 A。
4. 点击报告 A 中的“重新选择参数 / 测算其他币对与金额”。
5. 观察到报告 A 被新表单替换；完成下一次测算后，无法在原位置查看报告 A 并与新报告对比。

### 预期行为

在同一个聊天窗口里保留报告 A，另发新的测算表单；下一次测算完成后，另发报告 B。用户可以上下翻阅历次报告，无需重新创建会话。

### 原因定位

这是修复前的卡片更新逻辑导致的，不是机器人必须清除历史报告的限制。

- `liquidity_analysis/lark_card.py`：结果卡片中的“重新选择参数”按钮触发 `ACTION_OPEN_QUERY_FORM`。
- 修复前，`liquidity_analysis/lark_bot.py` 的 `LiquidityBotHandlers.on_card_action()` 在处理该动作时构建新表单，并通过 `_card_response(card, ...)` 返回。
- `_card_response()` 将新表单放进回调响应的 `card` 字段，触发对被点击消息的卡片替换，因此原报告消失。
- 测算完成后，现有代码已通过 `_send_to_user()` 另发结果卡片；本问题主要发生在从结果报告再次打开表单的环节。

相关路径：修复前，点击报告中的“验证 Maker 挂单”时，也会通过回调返回等待卡片，覆盖原测算报告。本次已一并修复。

### 已实施的修复

1. 点击“重新选择参数”时，回调只返回 Toast 提示，保留原报告。
2. 在后台另发新的查询表单，沿用原报告按钮携带的参数，供用户调整。
3. 保持测算结果以新消息发送，每次测算形成独立报告。
4. 点击“验证 Maker 挂单”时同样保留原测算报告，原有等待提示卡片和验证结果另发消息。
5. 网络请求继续放在后台执行，避免超过卡片交互回调的 3 秒响应窗口。
6. 按用户要求收敛为最小改动：卡片标题、正文、按钮文案和布局均保持原样，只调整报告相关操作的卡片发送方式；参数错误与未知操作继续使用原处理逻辑。

### 验收标准

- 连续完成至少三次测算后，每次结果报告仍可在聊天记录中查看。
- 从任一历史报告打开新表单，不改变该报告的正文。
- 点击挂单验证后，原测算报告仍保留，验证结果单独显示。
- 新表单带入原报告对应的参数，用户可以修改后继续测算。
- 回调及时响应，后台测算失败时也不覆盖历史报告。

### 当前进度

2026-10-21 完成本地修复并按用户要求收敛为最小改动。每次 Bug 修复只新增一个测试；本次在 `tests/test_lark_bot.py` 中仅保留一个针对报告再次打开表单的回归测试。原有 7 个测试未改动，当前全量测试通过（8 passed）。

该测试使用真实 Lark SDK 回调对象、序列化器和消息请求构建器，验证重新打开表单时回调不包含 `card` 字段，并在后台另发带有原参数的新表单；未保留其他新增测试。

尚未部署或重启机器人，未向真实 Lark 用户发送测试消息。运行新代码后需在 Lark 客户端验证连续测算和上下翻阅历史报告。

## BUG-002：无新操作时收到额外查询卡片

2026-10-27 用户反馈 15:06 和 15:10 未发送新消息却收到查询表单。当天本机只有一个机器人实例；旧日志仅记录连接与错误，没有收到消息或发卡成功的记录，因此不能据此确认这两次的实际触发来源。代码不存在定时发卡任务。

已确认消息入口没有检查 sender_type 或按 message_id 去重，并同步调用发送接口，可能阻塞事件确认；重新打开表单的卡片回调也未去重。

修复内容：只响应 sender_type=user 的消息；消息按 message_id 去重，卡片操作按 event_id 去重；正式运行使用 SQLite 保存接收记录，重启后继续生效；消息回复移到后台；日志记录事件标识、消息创建时间、触发类型以及发卡成功/失败，不记录消息正文或回调 token。可通过 LARK_STATE_DIR 指定状态目录，默认使用项目下的 .runtime/lark。

新增一个离线回归测试，覆盖非用户过滤、后台回复、不同 event_id 的同一消息重推、并发重复、重启后的去重、新消息正常回复，以及重新打开表单的重复回调。原有卡片布局改动保留。

全量测试通过（17 passed，SDK 原有事件循环弃用警告 1 条）。真实 Lark 收发效果仍需用户操作验证，旧日志无法追溯的两次发卡原因不作为已证实的根因。
